# Planning and evidence contract

## Project mode preflight — before creating any file

The root coordinator calls quality_info and resolves the current project in project_profiles before drafting artifacts. If its mode is repository-native, read its listed authorities and instructions. In that mode, the portable protocol below DOES NOT APPLY: no generated docs/superpowers spec/plan/contract, .quality ledger/reviews/evidence, synthetic contract/snapshot IDs, portable CLI execution or quality_gate PASS. Keep requirements, plans, approval quotes, original review findings and progress in the current task context or the repository-authorized system. These are not new repository authorities.

Retain cloud planning/independent review and the same local worker for code/tests/repairs. Select actual checks from the repository rules and the task's real impact; existing native test/architecture/CI gates own acceptance. Preserve required independent review, finding IDs, severity/impact/confidence, repair value/cost/regression risk and explicit deferral decisions in task context. Report native evidence and missing lanes accurately; registration, a fingerprint check or REPOSITORY_NATIVE_REQUIRED is never a product PASS. Material plan changes follow the repository's approval rules. If native prepare/run/gate is called accidentally, it returns REPOSITORY_NATIVE_REQUIRED without executing or writing; do not retry with a fake contract or raise the snapshot limit. A repository requiring artifacts outside its source is not permission to write arbitrary external folders or expand tool access.

For a portable project, continue the protocol below unchanged. Missing registration is a setup blocker, not permission to choose a weaker mode.

Retain project governance and the existing two real approvals. Do not implement before the plan is approved. Facts, assumptions and unresolved questions are separate. A critical unknown requires investigation, not invented certainty.

1. Read repository rules and actual interfaces/callers. Use GrillMe for unresolved business decisions. Write requirements with IDs, sources, observable behavior and boundaries. User confirms requirements/design.
2. Draft proportionate design/tasks plus one canonical JSON contract under docs/superpowers/specs/ or plans/. Use quality_resource names schema/contract and schema/policy for public schemas, and schema/review for report format. Do not read installation folders through external filesystem tools. Actual requirement semantics live in this one contract and linked official project documents; do not duplicate or override the project's authority. Markdown is its readable explanation.
3. Each necessary REQ must have a task and at least one acceptance criterion (AC). Specify input domain, expected outcomes and the source of that expectation; add appropriate negative/boundary/failure/recovery/concurrency cases. Specify module responsibilities, allowed dependency direction, ownership, interface/error semantics, migration, non-goals and real verification environment. Avoid prescribing full implementation/test bodies.
4. Call quality_info to learn registered projects. quality_prepare(project, contract-relative-path) validates the contract and returns its semantic contract_id, current snapshot and required reviews. Before the plan approval use approvals.plan="PENDING"; semantic ID intentionally excludes approval quote metadata. The actual design/plan quotes must be recorded before the local runner is allowed. Simulated fixture approval is explicitly labeled; never describe it as real user approval.
5. Dispatch fresh cloud-plan-review with the real spec/plan, contract, current facts, known policy lane IDs and the actual configured model. It independently checks completeness/feasibility/acceptance, and returns original text plus schema-valid review JSON kind=plan with contract_id (snapshot_id may be empty for plan review). Fix plan blockers and re-review before user plan confirmation. No automatic approval by silence.
6. Before plan confirmation, cloud-workflow may persist original plan-review artifacts ONLY under docs/superpowers/plans/reviews/ (already within its plan-document write scope). Save every schema-valid round as plan-<round>.json and original text as plan-<round>.md. A non-schema raw report goes in raw-plan-<round>.md, never among gate JSON files; preserve it verbatim and mark it incomplete, not passed. Call quality_prepare with plan_reviews=[latest-plan-json-relative-path]; its plan_gate must be PASS before asking for plan confirmation. Historical plan findings within the same semantic contract close with evidence="contract:<current-contract-id>" and a concrete independent document verification reason; no implementation lane is required or claimed at this stage. A newer complete plan round can supersede an incomplete backend round, but actual previous blockers still require explicit closure. After actual plan confirmation, preserve the exact quote. The parent preserves plan originals and directly archives source-review originals only under .quality/reviews/; do not ask the local model to retype them. Only local-worker writes implementation/tests, runs shell, and persists execution logs/run receipts; root may archive review text/JSON in its narrow report scope. It must not edit the private approved project policy or weaken assertions/thresholds/ignores. Requirements or constraints materially changing require renewed confirmation; routine implementation fixes do not.
7. Local verification command (the actual registered policy lives outside source):

`__PYTHON__ -m workflow run --settings __SETTINGS__ --project <registered-root> --contract <relative-contract.json>`

Run from `__RUNTIME__` (use the runtime directory as cwd); paths with spaces must be passed as quoted argv, not interpolated shell fragments. This writes .quality/evidence.json and complete logs. No cloud shell is needed. The parent checks quality_gate rather than trusting a passing summary. If registration is missing, report one-time setup needed; never invent registration or substitute arbitrary commands.

If an approved check conflicts with the approved plan or actual target count, STOP and return the conflict to cloud-workflow. Do not add a facade, dummy module, extra target or unrelated test solely to reach a minimum count; do not change the private policy, counts or plan yourself. The coordinator obtains an explicit policy/plan decision, independently reviews any changed plan, and renews the affected approval before resuming. A passing scan of unnecessary added files does not close this conflict.

Keep worker handoffs concise (normally 300-600 words): actual changed files, current snapshot/run IDs, real lane results, unresolved findings and exact existing artifact paths. Full command output stays in original logs; do not copy long logs or skill bodies into ledgers or responses. Read the actual evidence keys (`run_id`, `snapshot_id`, `lanes[].id/status/exit_code/checks/log`) rather than guessing aliases or directory layouts. Missing fields/files are missing evidence, not a reason to invent a receipt or repeatedly rerun checks. After a check completes and its artifacts are verified once, hand back `awaiting_review`; do not preempt cloud audit or create a final verdict yourself.

8. All original reviews and follow-up evidence remain versioned. A current run may replace .quality/evidence.json as the latest index, but unique original logs and run receipts remain; the latest attempt is selected by the gate, and an interrupted/failed newer attempt invalidates an older PASS. Reviews are persisted per round before latest pointers are updated. Finalization never edits source/spec/tests. Re-run quality_gate after finalization and only deliver valid PASS/PASS_WITH_DEBT with the exact source snapshot and limitations.

The root coordinator dispatches code/structure/test reviews as flat sibling sessions, never asks a child reviewer to spawn deeper children. Supply the selected pinned BMAD lens resources and actual scope to each sibling, collect all original reports through native callbacks, and return sibling evidence to code review for triage if needed. A host depth limit is a compatibility fact, not permission to silently omit a required lens.

Minimal JSON shape, fields and types are defined by schemas, with canonical example via quality_resource(name="example/contract"). Read the canonical example via project preparation or the repository example during setup, not by expanding filesystem access. The runner enforces real nonempty check output; parser unittest reads actual unittest summary. A json lane must output exactly {"checks": N, "skipped": 0, "failures": 0}; its underlying tool/wrapper is part of the approved project policy and must actually check those targets. Empty scans or handwritten success counters are not valid evidence.

The gate checks artifact consistency, not human signatures or semantic truth. A same-user process can forge files; independent CI/permissions are needed for stronger enforcement. Do not claim local script PASS establishes protected remote merge or universal correctness.
